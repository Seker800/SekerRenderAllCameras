# 分版本 Blender 适配与发布矩阵实施计划

- 状态：ACTIVE
- 日期：2026-09-16
- 目标版本：0.6.0
- 入口：版本配置、Blender/Presentation 宿主适配、构建脚本、全量测试入口、发布门禁和安装文档
- 权威来源：本计划、`PLAN.md`、`Docs/architecture/`、各目标版本配置、目标版本测试报告
- 前置依赖：Blender 4.0.2、4.1.1、4.2.0、4.5.13 LTS、5.2.1 LTS 可执行文件
- 阻塞：无；任何单版本 GUI 或安装态失败都会阻断该版本发布包，不由其他版本通过结果抵消

## 用户可观察结果

- 下载页明确提供五个与 Blender 版本一一对应的安装包，用户不再面对“一个通用包可能可用”的模糊承诺。
- Blender 4.0.2、4.1.1、4.2.0、4.5 LTS、5.2 LTS 分别安装、启用、显示面板并完成真实批量渲染。
- 每个发布包只声明并承诺自己的目标 Blender 系列；拿错包时在安装或启用阶段明确失败，而不是运行到渲染途中才暴露不兼容。
- 每个目标版本都有独立测试报告、安装态验收、GUI 验收和包哈希；某版本未通过时只阻断该版本，但不得把未通过版本标成受支持。

## 范围、非目标与不可变边界

- 范围：五个版本配置、按版本组装的宿主实现、五个发布包、逐版本测试矩阵、发布门禁、安装说明和兼容声明。
- 非目标：制作一个包含大量运行时版本判断的通用 ZIP；支持 Blender 3.x；自动兼容未来 Blender；改变现有输出命名、通道、目录、覆盖和恢复语义。
- 公共 Domain/Application/Infrastructure 仍可复用，但不得读取 `bpy`、判断 Blender 版本或拥有 GUI 调度状态。
- `bpy`、渲染 handler/timer、窗口/区域上下文、合成器 API、安装清单和包型差异均由目标版本宿主实现拥有。
- 插件不保存 `.blend`，不永久改变活动 Camera、帧、渲染器、输出、Film Transparent、色彩管理、对象/材质/节点或“渲染显示方式”。
- 输出仍固定写入 `.blend` 同级 `SekerRenderAllCameras/`；新生成同名文件覆盖，本次未生成旧文件保留。

## 当前实现、所有权与公开契约

- 当前构建只有一个 4.2+ Extension 和一个 4.0–4.1 Legacy 包，清单与运行时代码隐含“尽量通用”的方向，不能证明每个目标版本的 GUI 与安装行为。
- Domain 拥有批次、Camera、Channel、文件名和颜色映射等纯规则。
- Application 拥有批次编排公开契约；只依赖抽象端口，不依赖具体 Blender 版本。
- Blender Adapter 拥有场景读取、渲染、临时数据、状态快照与恢复。
- Presentation 拥有 Operator/Panel 和目标版本的事件循环接入，但不得复制 Application 编排规则。
- 构建配置是“目标版本 → 包型、清单版本边界、宿主实现、测试可执行文件、产物名”的唯一真相源。
- 目标产物：
  - `camera_batch_renderer-0.6.0-blender-4.0.2.zip`
  - `camera_batch_renderer-0.6.0-blender-4.1.1.zip`
  - `camera_batch_renderer-0.6.0-blender-4.2.0.zip`
  - `camera_batch_renderer-0.6.0-blender-4.5-lts.zip`
  - `camera_batch_renderer-0.6.0-blender-5.2-lts.zip`

## 方案比较与决策

### 方案 A：五份完整源码分支/目录

- 优点：隔离最彻底，每个版本可以任意修改。
- 缺点：Domain、命名、清单、通道和修复会复制五次，极易漂移；同一缺陷需要多次修复和验证。
- 结论：拒绝。版本隔离不等于复制业务系统。

### 方案 B：单一运行时根据 `bpy.app.version` 大量分支

- 优点：只发布一个包，短期构建简单。
- 缺点：继续走“通用版本”路线；未执行分支难以证明；清单无法准确表达支持范围；版本差异会渗入共同宿主路径。
- 结论：拒绝。

### 方案 C：共享纯核心，五个构建目标分别装配具体宿主实现

- 优点：业务规则单一；发布物中只包含目标版本所需的宿主策略；可以对 GUI 调度、API 和清单分别验收；下载和故障归属清晰。
- 缺点：构建、测试和发布资产数量增加，需要严格的目标配置和门禁。
- 结论：采用。源码允许复用小型、版本无关的 Adapter 工具，但发布物不得靠运行时版本路由选择宿主实现。

## 反打洞审查

- 不在 Domain/Application 加入 `bpy.app.version`、`bpy.context` 或 GUI timer。
- 不通过模块全局变量承载批次唯一状态；状态仍由运行会话/Coordinator 拥有，版本驱动器只持有本次 Operator 生命周期句柄。
- 目标版本和产物名只在版本配置维护一次，构建、测试和发布门禁读取同一配置。
- 不为测试创建绕过真实 Operator 的“测试专用成功路径”；host control 只作为宿主基线诊断，不替代插件 GUI 验收。
- 不保留第二条未经发布包安装的渲染路径作为验收依据；源码测试与安装态测试都必须通过。

## 里程碑与验收

### M1：冻结失败基线并整理未提交改动

- 路径：`scripts/run_full_test_suite.ps1`、`scripts/run_blender_edge_cases.py`、`scripts/run_gui_render_tests.py`、`build/test-reports/`
- 结果：测试进程硬超时、成功标记、隔离用户配置、同版本 demo 生成均可靠；现有五版本失败可复现且不会误报成功。
- 停止条件：测试会修改真实用户配置、用户 `.blend` 或无法按 PID 终止自身测试进程。

### M2：建立五个构建目标和确定性产物

- 路径：`scripts/`、`camera_batch_renderer/blender_manifest.toml`、新增版本配置/装配目录、`dist/`
- 结果：一次构建生成五个命名明确的 ZIP；4.0/4.1 为 Legacy，4.2/4.5/5.2 为 Extension；每个包包含目标宿主实现和准确版本约束。
- 停止条件：必须复制 Domain/Application 才能构建，或包内仍包含运行时自动选择五套宿主实现的路由器。

### M3：逐版本解决真实 GUI/宿主差异

- 路径：`camera_batch_renderer/blender/`、`camera_batch_renderer/presentation/`、对应测试
- 结果：4.0.2、4.1.1、4.2.0、4.5.13、5.2.1 各自在自己的宿主驱动下完成三 Camera、多通道 GUI 批次、取消和失败恢复。
- 停止条件：修复会永久改变用户 Blender 状态，或只能通过隐藏/禁用真实面板来通过测试。

### M4：逐包安装态、发布门禁与文档闭环

- 路径：`scripts/release_gate.py`、`README.md`、`Docs/reference/`、`Docs/workflow/`、changelog
- 结果：五包分别安装、启用、渲染、禁用/卸载；版本错配被拒绝；报告记录版本、用例、结果、日志、包哈希。
- 停止条件：任何受支持版本缺少真实 GUI 或安装态证据。

## 验证矩阵

- 纯 Python：Domain/Application/Infrastructure 单元测试、版本配置解析、目标装配、错误版本拒绝、确定性构建。
- 架构：`bpy` 依赖方向、唯一 Adapter、公共核心无版本判断、发布包只含一个目标宿主实现。
- 每个 Blender 后台：注册/注销、Beauty/Alpha/Object ID/Material ID、格式矩阵、Render Border/Crop、Compositor/File Output、取消、异常、清理和状态恢复。
- 每个 Blender GUI：真实 VIEW_3D Operator、三 Camera、多通道、渲染窗口偏好抑制与恢复、停止当前图片后退出、连续第二次运行、窗口关闭/超时保护。
- 每个包安装态：干净隔离配置中安装、启用、双面板、demo 渲染、禁用/卸载、错误版本安装拒绝。
- 失败/取消：文件写入失败、handler 信号异常、无 Camera、未保存、只读目录、同名 Camera、渲染器不支持辅助通道；不得残留临时 Scene/Object/Material/Node 或用户状态。
- 性能：版本装配不进入逐像素热路径；记录三 Camera 四通道耗时和峰值内存，只做回归警戒，不牺牲正确性。

## 幂等、失败恢复、回滚和文档影响

- 构建写入临时 staging，验证成功后原子替换同名产物；重复构建应得到相同文件哈希。
- 测试只使用 `build/` 下隔离配置、临时场景和输出；失败保留报告/日志，成功也保留摘要，不写真实用户配置。
- 运行失败沿用 `.incomplete` 与 RenderInfo 语义；已成功图片保留，未完成项可辨识。
- 回滚以目标版本为单位：可以停止发布单个失败包，不影响已通过版本；代码回滚不得恢复“一个通用包”的兼容声明。
- 更新架构版本边界、实现现状、全量测试流程、测试范围、README 安装选择和 changelog。

## 发现与决策

- 首轮矩阵中 Blender 4.2 GUI 崩溃、4.5 GUI 超时、5.2 环境/GUI 崩溃，证明后台公共逻辑通过不足以代表用户可用。
- Blender 4.5.13 的直接宿主异步渲染基线可通过，但当前插件批次在首张图后无法可靠恢复调度；差异属于版本宿主/GUI 驱动，而不是 Domain 规则。
- 4.2 不能读取由 5.2 保存的 demo `.blend`；安装态 fixture 必须由目标 Blender 自己生成。
- 本计划取代此前“4.0.2+ 单一兼容范围”的发布解释；历史计划保留为历史事实，不再作为当前支持策略。
