# 全量测试流程

## 目标与发布原则

测试责任属于开发与发布流程，不转嫁给用户。发布候选只有在自动化、真实 Blender、GUI、安装包和版本矩阵均留下可复查证据后才能标记通过；缺少目标版本、脚本未执行或结果不可复查，一律记为“未验证”，不能写成“通过”。完整范围与当前自动化映射见 [`测试范围与发布验收矩阵.md`](测试范围与发布验收矩阵.md)。

## 唯一全量入口

在仓库根目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/run_full_test_suite.ps1
```

脚本默认使用 `PATH` 中的 Blender，顺序执行纯 Python、架构、静态检查、目标源码装配、真实渲染、边界矩阵、GUI、五包构建、发布门禁、隔离安装、安装态演示和卸载。结果保存在 `build/test-reports/<时间>-<PID>/summary.json`，每个步骤都有独立日志；任一步失败时脚本最终退出非零。

发布前必须显式传入全部目标版本，不能只用开发机默认 Blender：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/run_full_test_suite.ps1 `
  -Release `
  -BlenderPaths @(
    'C:\Path\Blender-4.0.2\blender.exe',
    'C:\Path\Blender-4.1.1\blender.exe',
    'C:\Path\Blender-4.2.0\blender.exe',
    'C:\Path\Blender-4.5-latest\blender.exe',
    'C:\Path\Blender-5.2-latest\blender.exe'
  )
```

`-SkipGui` 只允许用于无图形会话的中间检查，不构成发布验收。

## 执行阶段

1. 纯 Python 与架构门禁：Domain/Application 规则、状态机、命名、原子清单、兼容层、依赖方向和版本一致性。
2. Blender 源码态后台测试：注册/注销、四个单通道与组合通道、空选择拒绝、像素调色板、取消、单项失败、批次失败、隐藏工作目录、环境配对和状态恢复。
3. Blender 边界矩阵：未保存文件、零 Camera、不支持格式、Multi-view、透视/正交、隐藏 Camera、名称清理冲突、PNG/JPEG/TIFF/OpenEXR、Compositor/File Output、Render Border/Crop 和不保存 `.blend`。
4. GUI 测试：先运行不启动插件批次的宿主异步渲染基线，再从真实 3D View 上下文运行三 Camera 插件批次、Material ID-only 连续批次、空选择报错、协作式停止、弹窗偏好恢复和运行时状态清理。
5. 专项验收：灯光/World 配对的实际图像差异，Material ID 逐面/未分配材质的逐像素一致性，50 Camera 与连续十批压力烟测，以及相邻版本错包拒绝。
6. 构建与发布门禁：按目标配置生成五个有版本上下界的 ZIP；除入口、清单和固定宿主策略外，共享功能文件逐字节一致。
7. 安装态验收：隔离用户配置安装、启用、检查产品名与面板四开关、完整四通道演示、逐个单通道和全不选拒绝、禁用/卸载；每个 Blender 只使用与自身精确匹配的包。
8. 跨版本契约：比较五个安装态演示的 UI 选项、默认值、单通道结果数/通道、完整结果、清单结构和 ID 调色板，任一版本语义漂移即失败。

后一步不能替代前一步。例如源码态渲染通过不能证明 ZIP 可安装；5.2 通过不能证明 4.0.2 兼容；后台通过不能证明 GUI Modal 调度可靠。

## 必测不变量

- 活动 Camera、当前帧、输出路径、格式、引擎、色彩管理、Film、Render Border、Compositor、World、灯光和 Collection/View Layer 可见性保持任务前值。
- Object/Material 的颜色、材质槽、逐面材质索引、Pass Index 和节点保持不变。
- 正常、取消、单项失败和批次异常后均不残留临时 Scene、Object、Mesh、Material、Image、handler、timer 或 staging。运行期文件只允许进入一个 `.render-all-cameras-work/`；成功后该目录消失，取消/失败后其中只保留 `.incomplete`，输出根目录不得出现零散 marker/tmp。
- 插件不保存或改写用户 `.blend`；测试比较运行前后文件字节。
- 同一输入的 Camera 顺序、清理后文件名、冲突后缀和 ID 颜色确定；四通道像素尺寸一致；执行动作数严格等于 Camera 数乘以已选通道数。
- 仅成功完成的新图原子替换同名旧图；未选择、未执行、失败或取消的旧图以及目录内无关文件保持不变。
- RenderInfo/ID 清单与实际文件、状态、环境配对和调色板一致；失败后仍保留上一份有效 JSON 和 `.incomplete`。

## 结果判定与证据

- `passed`：该目标版本、该用例、该构建产物本次实际执行且断言通过。
- `failed`：断言、进程退出码、超时、崩溃、像素不一致、状态泄漏或安装失败。
- `not_run`：缺少目标版本、GPU/渲染器、图形会话或 fixture。`not_run` 不是通过；发布要求项出现 `not_run` 时必须阻断发布。
- 每次发布保存 `summary.json`、各步骤日志、五个 ZIP 的 SHA-256、目标 Blender 精确版本和专项验收产物路径；摘要中的 `failed` 与 `not_run` 都必须为 0。
- 正式 Release 上传后运行 `python scripts/release_gate.py --verify-online`，逐个下载五个线上资产并与本地已测试 ZIP 的 SHA-256 对照。

修复失败后必须重跑失败用例、所属层和完整发布套件，不能只重跑单个断言后直接发布。

## 开发机持久安装约定

- 开发者需要直接人工验收时，为每个 Blender 使用对应目标包安装到真实用户配置，启用后保存偏好；测试完成后保留插件，不执行卸载。
- 每个 Blender 使用自己生成的演示 `.blend`，测试场景和输出保留在 `build/persistent-install-tests/<精确版本>/`，便于再次打开检查。
- 安装或更新真实配置前必须先备份该版本的 `config/` 和现有插件目录；Blender 正在运行时不得覆盖插件或 `userpref.blend`。
- `run_full_test_suite.ps1` 的隔离安装生命周期仅用于发布包安装/卸载门禁。所有 `BLENDER_USER_*` 目录必须先实际创建；缺少目录时不得启动 Blender，防止回退到真实用户配置。
